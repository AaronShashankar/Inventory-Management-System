# Identity lifecycle and organization settings

Implementation: `accounts/views.py` and `accounts/services.py`.

Login validates a username/password with Django's password hasher, establishes a session, and rotates CSRF. No password is returned. Membership authorization runs for each request; write services check again after the organization lock. Reassigning roles and disabling memberships uses the same lock, so a mutation sees a committed authorization state.

`update_member` reloads the membership under the tenant lock and prevents removal of the final active administrator. Inviting a new email creates an unusable password and sends a Django signed, one-hour setup token after the membership transaction commits. Existing users gain only the requested membership. Reset confirmation locks the user row and validates the token and password before changing the hash; a used token cannot be replayed. Configure email delivery monitoring; synchronous send failure can occur after membership commit and requires a reset request or operational retry.

Organization settings allow an administrator to change the business name and initial three-letter currency code. Once any product exists, a base-currency change is rejected because stored reference prices would otherwise be reinterpreted. This is a guard against accidental relabeling, not currency conversion. Currency codes should be chosen from ISO 4217 by the business administrator; the API enforces uppercase three-letter shape, not a maintained ISO registry.

A request UUID is generated by middleware, propagated through a context variable to audit events, returned as a response header, and emitted in JSON logs with method/path/status/duration. Bodies, tokens, and cookies are not logged. Management commands have no HTTP request ID.
